# Security & integrity

Threat → control → where it is tested.

| Threat | Control | Tests |
| --- | --- | --- |
| Telegram spam farming | Deterministic filters (dup/rate/burst/short/low-value/link/forward), daily qualification cap, auto-flag + admin review, recompute from features | `telegram-scoring`, `integration/telegram` |
| Duplicate Telegram identities / username changes | Numeric `telegram_user_id` is the key; usernames are display data; unique constraints on hero↔user and claim↔user | `integration/telegram`, `integration/identity` |
| Forged / replayed Telegram login | HMAC verification, ≤ 5 min age, single-use payload hash | `integration/identity`, `security/http` |
| Hero takeover via username | Hero is resolved from the session's numeric id; body-supplied ids ignored; DB blocks a second claimant | `integration/identity`, `security/http` |
| Forged wallet ownership | Server-issued, expiring, single-use challenge; server rebuilds the message; ECDSA recovery must equal the challenged address; one wallet ↔ one hero | `integration/identity` |
| Client-modified stats / Gold / ownership | Browser never writes game state; all mutations are server routes; RLS denies API roles; Gold only via ledger triggers | `security/rls`, `security/http`, `integration/economy-inventory` |
| Duplicate / replayed rewards | `idempotency_key` unique, settlement status gate, unique `source_ref` for drops | `integration/economy-inventory`, `integration/arena` |
| Queue manipulation / unfair turns | CSPRNG seed stored with cycle; persisted order; carry-forward instead of padding; one entry per hero per cycle | `unit/arena-queue`, `integration/arena` |
| Concurrent settlement / races | `arena_state` row lock; `UPDATE … WHERE status='SIMULATED'` gate; concurrent `advanceArena` tested | `integration/arena` |
| Tampered battle history | Inputs frozen by trigger once simulated; replay re-simulates and checks the hash | `integration/arena`, `unit/combat` |
| Malformed / hostile webhook | Secret header (constant-time), size caps, strict parsing that never throws, official-chat filter | `security/http`, `unit/telegram-scoring` |
| CSRF | Same-origin `Origin` check on every cookie-authenticated mutation + `SameSite` cookies; JSON-only bodies | `security/http` |
| Session theft / fixation | HMAC-signed, HttpOnly cookies; revocable via per-user epoch; banned users lose access at once; admin cookie is `SameSite=Strict`, 8 h | `integration/identity`, `security/http` |
| Admin brute force | 5/min per IP + delay; admin disabled unless `ADMIN_ACCESS_KEY` (≥ 24 chars) is set; every admin write audit-logged (append-only) | `security/http` |
| Direct DB access via Supabase keys | RLS enabled on **every** table, **no policies**, privileges revoked from `anon`/`authenticated`, functions not executable; `clank_harden_schema()` re-applies after future migrations | `security/rls` |
| Free-pick identity forgery / CSRF | Member = the signed session's Telegram id (body-supplied identity is a 422); same-origin check; strict JSON body; 30 picks/min/member | `security/picks-http` |
| Late / duplicate / changed-after-lock picks | Server-clock window (`starts_at` ≤ now < `combat_starts_at`); PK `(battle, member)`; `locked_at` + guard trigger; shared battle-row lock vs settlement | `integration/picks`, `security/picks-http` |
| Pick for a hero who isn't fighting | Composite FK `(battle_id, character_id) → arena_participants` | `integration/picks` |
| Reading the winner before picks lock | Replay served only from `combat_starts_at`; state publishes no ranking/winner; the next group's roster is not published | `integration/arena-state`, `security/http` |
| Pick-reward replay / double pay | Ledger `idempotency_key` per (battle, member); resolved picks frozen by trigger; settlement inside the one-shot battle transition | `integration/picks` |
| Hero rename abuse / hostile names (markup, control or bidi characters, invisible names, huge names) | One validator shared by UI and server (`validateRpgName`): NFC, ≤ 32 code points, no control/bidi/zero-width characters, no `< > \``, must contain a visible character; the database repeats the control-character rule as a `CHECK`; names render as plain text | `unit/rpg-name`, `integration/hero-admin`, `security/hero-admin-http` |
| Rename used to move ownership / history | A rename writes `name_override` (+ who/when) and one audit row, nothing else; ownership, claims, wallets and history are keyed by the immutable Telegram id / character id, never by name | `integration/hero-admin` |
| Non-admin renames / edits a hero's class, stats or identity | Admin session required (closed otherwise); same-origin on writes; a signed-in owner is not an admin; the general hero PATCH refuses class, stats, XP, level and identity fields; class change is also blocked by a DB trigger | `security/hero-admin-http`, `integration/hero-admin` |
| Eligibility card leaking scoring internals / inviting spam / inventing progress | Copy is high-level only ("qualifying messages", headline threshold from settings); numbers appear only from the member's server-verified stored count; flagged members get a neutral review message | `unit/hero-eligibility`, `security/hero-admin-http` |
| Betting / wagering / deposits / escrow | **Do not exist.** The betting design was abandoned before it was ever applied anywhere; there is no bet, deposit, escrow, odds or withdrawal table, flag, setting or route (asserted by `security/rls`). Arena Picks are free | `security/rls` |
| Reward double-credit / per-battle emission (scoring replay, retry, two workers, crash mid-way, finalization replay) | **No token is credited per battle**: the ledger has no such kind (a CHECK refuses it). One scoring settlement per battle (`UNIQUE(battle_id)`), one score row and one Points row per (member, battle); a board is finalized once (`PRIMARY KEY (kind, period_start)`) and credits one base row and one bonus row per (member, period) (partial unique indexes + idempotency keys); scoring and finalization are single transactions | `integration/rewards-scoring`, `integration/rewards-boards`, `integration/rewards-migration` |
| Reward rounding / money creation | Integer LOGICAL micro-tokens (`bigint`/`numeric(78,0)`; no float, no contract decimals inside a finished board); `awarded + returned = pool` is a DB CHECK per board; a bonus is exactly `div(base × bps, 10000)` (DB CHECK) and exists only on an earned prize; the remainder returns to the reserve, never to a random member; `earned = claimable + reserved + claimed` is a DB CHECK per account; the ledger is append-only | `unit/rewards-leaderboard`, `unit/rewards-domain`, `integration/rewards-claims`, `integration/rewards-migration` |
| Sybil / bot farming | 1 Telegram id → 1 hero (UNIQUE) → ≤ 1 pick per battle (PK); eligibility = Telegram identity + ≥ 50 qualifying messages from the official community + an active hero; REVIEW/SUSPENDED states hold prizes and claims or block credit; one holder wallet ↔ one account (trigger + unique index, admin-approved exceptions only); admin analytics, no auto-ban | `integration/rewards-picks`, `integration/rewards-claims`, `integration/rewards-admin` |
| Leaderboard gaming / paying for rank | Every valid pick counts toward BOTH boards and there is no scoring cap (migration 1400 removes the per-day counting columns and trigger; the only database guard refuses a score row for an already finalized day/week); holder tier, balance, wallet age and account age never enter scoring, ranking, ties or the base prize (pinned structurally and by a played-out FREE-vs-holder comparison); ties are exact (correct picks + accuracy by integer cross-multiplication); a minimum number of valid picks (20 daily / 100 weekly) for prizes only; REVIEW/SUSPENDED/FLAGGED prizes are held for an admin | `integration/rewards-boards`, `integration/rewards-no-pay-to-win` |
| Prize double-pay / tampering / reset | Finalization is one idempotent transaction; finalized boards and their results are immutable (append-only triggers; only a HELD prize, or a bonus PENDING VERIFICATION, can transition — audited, once); there is **no reset-leaderboard** action; boundaries and countdowns are server-time (a client clock changes nothing) | `integration/rewards-boards`, `unit/rewards-leaderboard` |
| Late / changed / duplicate / racing picks | Server-clock lock at `combat_starts_at` (service + DB trigger); eligibility snapshot frozen at lock; PK makes duplicates idempotent; 20 simultaneous requests leave one row | `integration/rewards-picks` |
| Herding on the crowd | The shared payload has no counts; the per-fighter distribution is released only after the server clock passes the lock | `security/rewards-http`, `security/picks-http` |
| Double claim / overlapping claims / replayed tx | The whole claimable balance is reserved atomically (account row lock); one PENDING claim per member (partial unique index); a transaction hash can back only one claim (unique index); idempotency key per request; the amount is derived from the ledger — the body has no amount field; the claim's amount and destination are frozen by a database guard | `integration/rewards-claims`, `security/rewards-http` |
| Marking a claim SENT without a real payment | Payouts are **manual**: the application cannot send tokens. *Mark sent* is accepted only after the server reads the chain **read-only** and finds a *successful* transaction on the configured chain with enough confirmations (`minConfirmations`, 2) that emitted a `Transfer` of the **official token**; an unknown/unconfirmed/reverted transaction or an unreadable chain leaves the claim PENDING; marking twice or racing two admins completes it once | `integration/rewards-claims`, `unit/rewards-chain-reader` |
| Wrong recipient / amount / token / chain paid | The verified `Transfer` must go to the claim's **frozen destination** for exactly the claim's **frozen amount** (logical amount → the contract's `decimals()` read at verification → exact raw amount, to the unit; the admin is shown the exact figure to send; a CHECK ties `amount_raw` to `amount_micro`) on the frozen token and chain — else the claim stays PENDING with a precise reason; a denied claim returns its reservation to claimable (`CLAIM_RELEASED`) | `integration/rewards-claims`, `unit/rewards-chain-reader` |
| Payout-address typo / black hole / hijack | Destination validated server-side (EIP-55 checksum, zero/burn/precompile/token contract/reward wallet refused; another account's verified holder wallet refused and logged; a destination shared by several accounts is flagged for the admin); a custom destination is for **one payout only** and never changes the holder wallet or tier; changing the *holder* wallet needs a fresh Telegram sign-in and drops the tier; wallet history is audited | `integration/rewards-claims`, `security/rewards-http` |
| Treasury key exposure | **There is no key.** The application holds no signing key and never sends a transaction; `src/server/rewards/sender.ts` was deleted; `CLANKRPG_REWARD_TREASURY_PRIVATE_KEY` is retired (its value is never read — if present, Admin warns by variable *name* only); the chain reader is read-only; a production build is scanned for secret values | `unit/rewards-config`, `security/rewards-http`, build scan |
| Reward outage stalling the arena | Scoring, finalization and claims run off the request path in their own transactions and swallow/log failures; a quiet no-op if the migration is absent; tested with the scoring tables missing entirely | `integration/rewards-scoring` |
| Holder-bonus loophole: buy-before-close, sell-after, token hopping, stale data | The bonus is decided ONCE at the close from an append-only log of server-made on-chain reads (`arena_holder_observations`): it needs an unbroken run ≥ the tier threshold reaching back 24 h (daily) / 7 days (weekly) before the period began and through a fresh **close verification**; a gap > 6 h breaks continuity; a failed close read leaves the bonus PENDING (never granted blindly, never delaying the base prize); the database refuses an observation of any wallet but the member's current verified one; changing the wallet restarts from zero; honest limit: tokens are not locked, so this is *verified* — not perfect — continuity | `unit/rewards-holder-bonus`, `integration/rewards-holder-bonus`, `integration/rewards-holders` |
| Holder bonus taken from other players / inflating the pool | The bonus is extra on top of an already-fixed base prize; the base ladder is computed before and independently of any holder data (structurally tested); maximum exposure is a product of settings, shown in Admin | `integration/rewards-holder-bonus`, `unit/rewards-economy` |
| Fake holder (forged balance/tier/bonus/address) | The browser sends only a signature; the server issues the nonce/message, recovers the signer from ITS stored message, reads `balanceOf` itself; a typed payout address never creates holder evidence; strict bodies reject any balance/tier/bonus field; the official token address is the ONE server setting and the contract itself is authoritative for `decimals()`/`symbol()` (an unverifiable contract fails closed) | `integration/rewards-holders`, `security/rewards-http`, `unit/rewards-chain-reader` |
| Token hopping / one stack of tokens powering several accounts | One verified holder wallet ↔ one account (trigger + unique index); evidence belongs to the account bound at the time and a wallet change restarts continuity from zero; a receiving wallet has no history of its own; verification older than 6 h → NEEDS VERIFICATION; refresh is bounded (jittered schedule, backoff, manual 5-min rate limit) so the chain RPC cannot be hammered | `unit/rewards-holder-bonus`, `integration/rewards-holders`, `integration/rewards-holder-bonus` |
| Pay-to-win | Holder data is unreachable from stats, combat, RNG, pick results, scoring, ranking and the base ladder; a regression test pins it structurally and behaviourally (FREE and a 10M holder get the same 20 scored picks/day and the same points) | `integration/rewards-no-pay-to-win` |
| Points farming / double award | One Points row per pick (partial unique index); append-only ledger; unaffected by the daily scoring limit; no holder multiplier | `integration/rewards-scoring` |
| Client-modified identity / amount / address | Strict body schemas refuse unknown fields; identity is the session's Telegram id; amounts are computed on the server | `security/rewards-http` |
| Dev conveniences leaking to production | Dev login hard-disabled when `NODE_ENV=production`, demo heroes need explicit opt-in, dev secrets refused in production | `security/http` |
| Secret exposure | Server-only env, `server-only` imports, client-bundle audit (no secret *values*; names only appear in staff-facing copy that was removed) | build check |
| Browser choosing a reroll (seed / class / rarity / stats) | `POST …/reroll/preview` takes `{}` only; the seed is a server-side 128-bit nonce; Apply names a stored preview id; strict bodies refuse every other field; seeds never reach a browser | `security/hero-versions-http` |
| Two admins / a double click changing a hero twice | One transaction behind the hero's row lock; idempotent by preview id / request key; stale previews and screens refused; proven with parallel connections on real Postgres | `integration/hero-versions`, `…-postgres` |
| A hero changed after it was shown / picked in the Arena | Refused while the hero is in any unsettled roster (SCHEDULED / SIMULATED); the roster's foreign key serialises roster building with the admin lock; historical snapshots, hashes and replays are untouched | `integration/hero-versions`, `…-postgres` |
| Class / look / stats edited behind the version history | Deferred constraint triggers refuse a commit where the projection differs from the current version; versions are immutable; every hero must have a current version | `integration/hero-versions-migration` |
| Public hero pages leaking private data / moderation | Whitelisted fields only (no Telegram id, db id, seed, flags, notes, wallet); suspended / banned / unknown / malformed ids are one identical 404 (page and image) | `integration/public-heroes`, `security/hero-versions-http` |
| Hostile hero names in cards / share links | Text is cleaned and clipped, drawn with canvas calls (never markup); the share link is an `x.com/intent` URL built from public facts only; no remote fetch anywhere | `unit/hero-card`, `integration/public-heroes` |

## Known gaps (be honest before launch)

* **Admin auth is a single shared key** (HMAC-signed session cookie, rate-limited). Before real launch, put the admin behind SSO/2FA and give each operator their own identity; the audit log currently records the actor as `admin` (hero renames say so explicitly: "individual operator not identifiable").
* **In-memory rate limits** are per instance; add edge rate-limiting.
* The main suite runs on an embedded single-connection Postgres; true multi-connection contention is exercised only by `tests/integration/hero-versions-postgres.test.ts` (run it against a throwaway server with `CLANK_TEST_PG_URL`) — the other row-lock paths remain single-connection tested.
* The Telegram `message_reaction` and sign-in flows are fixture-tested, not live-tested.
* `NEXT_PUBLIC_*` values are the only browser-visible config; keep it that way.
